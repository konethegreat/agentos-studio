# 2.5.0 design: replayable run exports and offline mode

Date: 2026-11-23
Status: approved by the owner ("Let's do 2.5.0 with replayable run exports and offline mode")
Constitution: full autonomy, so open choices are decided here and recorded as assumptions.

## What already exists

- `timeline::format_markdown` and `timeline::export_markdown` write a run report to
  `04_Agent_Engine/runs/<id>.md`, and the Timeline screen has an Export button with a toast.
- `offline.rs` probes reachability and Ollama models, and `agent_limits::online()` caches the
  answer for 60 seconds. The scheduler holds every queued mission while offline, and the stuck
  watchdog ignores silence while offline. The status bar shows a one-shot offline chip.

So 2.5.0 is not a greenfield build. It closes the gaps between what exists and what the roadmap
idea promised: a report worth replaying, and an offline mode that keeps work moving when a local
model is available.

## Decisions

### Replayable run export

1. Keep one writer: `timeline::export_markdown`. It now goes through `Vault::write_note`, so the
   traversal guard and atomic write apply. The mission id is validated against
   `[A-Za-z0-9_-]` before it becomes a file name.
2. The report gains what a reader needs to replay it without the app: the provider next to the
   model, the reviewer verdict and note, the pull request link, the step count, and a closing note
   that long tool output is clipped by the source logs, not by the export.
3. Every text field still passes `constitution_gate::redact`.
4. Tests: a tempdir vault holds the written file with the expected sections; an id with `..` or a
   path separator is rejected with a clear error; the redaction assertion stays.

### Offline mode

1. One decision function, `offline::decide(online, auto, pin, active, models)`, returns
   `PinLocal`, `Restore`, `Forget` or `None`. It is pure and fully tested. Applying the decision is
   a thin function that calls the Hermes CLI through existing helpers and verifies the read-back.
2. The preference lives in the store kv as `offline.auto_local`, default on. The banner can turn it
   off; nothing else changes it.
3. A background loop in `lib.rs` runs every 60 seconds: it computes `offline::status()`, applies
   the decision, and emits `agentos://offline` with the status, the pin and the preference. The
   status bar and the new banner read that event; the status bar stops fetching once on mount.
4. Pinning means switching Hermes to the `local` provider (Hermes `custom`, base URL
   `http://localhost:11434/v1`) with the first model Ollama reports, through
   `hermes_engine::set_active_provider`. The previous provider, model and base URL are saved in the
   kv pin record. Hermes config is never edited by hand, and no secret is written.
5. Restoring happens only while the active provider is still the pinned local pair. If the owner
   switched providers during the episode, the pin is forgotten without touching config.
6. The scheduler gate becomes `online() || pinned_locally()`. With no network and no local model,
   the old behavior stays: nothing new starts and nothing is marked stuck. With a local pin,
   queued work starts on the local model. The stuck watchdog ignores offline silence only when
   there is no local pin, because a local model is expected to answer.
7. Banner copy: offline with a pin names the model and says cloud lanes resume later; offline
   without local models says work waits; offline with auto off offers to turn it on. No dismiss,
   because it states a live condition.
8. Tests: the decision table, the pin record round trip, the scheduler gate with and without a
   pin, and the stuck guard. Nothing in the tests runs the Hermes CLI; the apply step is not
   unit tested and is exercised by the owner in the running app.

## Assumptions

- The owner wants Studio to touch Hermes config automatically only in this one direction (offline
  local pin, restored on reconnect). Any other provider change stays manual.
- A local model runs through Ollama on 127.0.0.1:11434, which is the address the codebase already
  assumes.
- Exported reports live in `04_Agent_Engine/runs/` and are not indexed; the folder is the index.

## Out of scope

- Manual "pin now" buttons beyond turning automatic pinning on or off.
- Exporting raw worker logs (they can contain unredacted output; parsed steps are the record).
- Changing provider routing for kanban tasks beyond the Hermes config switch.
