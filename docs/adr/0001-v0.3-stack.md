# ADR 0001: stack changes for v0.3

Status: accepted (v0.3.0)

## Context

v0.3 adds a real terminal, update management, a workspace tree, GitHub and a permission layer. The v0.2 stack (Tauri v2, Rust, React 19, TypeScript, Tailwind 4) stays. The question was which pieces to add and which to refuse.

## Decisions

| Change | Why | Trade-off |
|---|---|---|
| `portable-pty` (Rust) | The WezTerm PTY layer: ConPTY on Windows, openpty elsewhere, one API. Interactive Hermes needs a real TTY for live reasoning, slash commands and typed approvals. | Adds the `winapi`-era dependencies of WezTerm. A hand-written ConPTY wrapper would be smaller but Windows-only. |
| `@xterm/xterm` + `@xterm/addon-fit` | The standard terminal emulator for web views (VS Code uses it). Handles ANSI, cursor movement, alternate screen, so Hermes's TUI renders correctly. | About 300 KB of JS. Nothing lighter renders full-screen TUIs. |
| `ureq` 3 (rustls) | Small blocking HTTP client for the GitHub releases API, the npm registry and changelog files. Runs on blocking threads, so no new async runtime coupling. | Pulls in rustls and webpki roots (about 1 MB in the binary). `reqwest` would bring hyper and more. Shelling out to `gh api` would fail for users without `gh`. |
| `sha2` | Verifies downloaded Studio installers against the GitHub release `digest` before running them. | Tiny. |
| `tauri-plugin-notification` | Native OS notifications for new versions (Windows toasts, macOS and Linux notification centres). | One more capability to grant. |
| SQLite `studio.db` (existing `rusqlite`) | Workspaces, folders, tags, attachments, policies and the audit log need relational queries and atomic updates. Already a dependency. | A second database next to Hermes's. Kept to data Hermes cannot hold. |

## Refused or deferred

- **Tauri updater plugin** (deferred). It needs a signing key pair, with the private key as a CI secret, and signed update manifests. That is the right end state, but it needs the owner to create and store the key. v0.3 downloads the release installer, verifies its SHA-256 digest from the GitHub API and runs it. Moving to the updater plugin is on the roadmap together with code signing.
- **Moving Hermes provider keys into the OS keychain** (refused). Hermes reads keys from its own `.env` and its credential pool. Moving them would break Hermes outside Studio. Studio-owned secrets will use the OS keychain (`keyring` crate) when Studio first needs one; v0.3 stores none. Hermes already supports external secret sources (`hermes secrets`, Bitwarden and 1Password), which Studio will surface instead.
- **A Studio-owned chat database** (refused). Hermes's `state.db` stays the source of truth; Studio stores placement only, so the terminal, the gateway and Studio always agree.
- **State libraries (Redux, Zustand), a component kit (MUI, shadcn), a router** (refused for now). The UI is a handful of views; React context and props are enough. Revisit when the view count doubles.
- **Two-way Notion sync engine in Studio** (deferred). Hermes already talks to Notion through the Notion MCP server. A Studio-side sync would duplicate auth and conflict handling. v0.4 adds a sync ledger in the vault (frontmatter `notion_id`, `synced_at`, content hash) and drives Hermes to apply changes.
